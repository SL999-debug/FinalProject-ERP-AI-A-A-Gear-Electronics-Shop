# 02 — The Airtable base

The machine-readable version of this page is [`../schema/schema.json`](../schema/schema.json).
That file was extracted from the dashboard's own `SCHEMAS` object, so it is not a hand-written
idealisation — it is what the application actually reads and writes.

## The six tables the app uses

| Table | Hebrew label | What it holds |
|---|---|---|
| `products` | מוצרים | Catalogue: name, SKU, category, price, stock, description |
| `customers` | לקוחות | Contact details and the `CUST00000x` key used by invoices |
| `leads` | פניות | Website prospects and the state of the cold-e-mail sequence |
| `orders` | הזמנות | Intended purchase records — **currently not persisted**, see below |
| `invoices` | חשבוניות | All three Israeli document types, distinguished by `InvoiceType` |
| `tasks` | משימות | Things a human must do; WF-1 raises them automatically |

The course template's base has more tables than this. These six are the ones the dashboard
exposes, and this repository documents what the project can actually reach.

## The one real modelling decision: one `invoices` table

The three Israeli document types — tax invoice (`חשבונית מס`), invoice (`חשבונית`) and receipt
(`קבלה`) — live in **one** table, separated by an `InvoiceType` field.

The alternative is three near-identical tables, which the template also allows. One table wins
here for a concrete reason: the director agent (WF-9) sums income and outstanding debt, and
that query is a single pass over one table instead of a three-way union. When a rule changes
about what counts as revenue, there is one place to change it.

The cost is that WF-8 has to switch on the field before rendering, and that any "total
invoices" figure is really "total rows, filtered by `InvoiceType`".

## Fields, and the ones that are quietly broken

`schema/schema.json` lists every field with its Airtable name and a flag for whether it is
actually persisted. Two entries are `null` there, and they are not typos in the schema:

**`orders` — all seven fields unmapped.** `number`, `customer`, `items`, `total`, `status`,
`date` and `notes` are all rendered in the form and all discarded on save. Creating an order
produces a row with every cell empty. This is the most serious functional bug in the project
and it is documented rather than hidden. See
[09-known-issues.md](09-known-issues.md#3-the-orders-screen-saves-nothing).

**`products.imageUrl` — collected, never stored.** The product form accepts an image URL and
the payload carries it, but the Airtable table has no image field, so the dashboard falls back
to a generated initial-letter avatar. The URL is accepted and then lost.

`products.InStock` *is* mapped, but Airtable stores it as text while the form sends a number,
which makes the save fail with HTTP 500. Also in the known-issues page.

## Relations are text keys, not Airtable links

`invoices.CustomerId` holds a string like `CUST000003`, not a linked-record id. So are the
`tasks`→customer and `tasks`→invoice references.

This was a shortcut. A linked-record field would have given referential integrity and a working
rollup for free; the text key gives neither, and it means the invoice form has to make the user
pick a code. The dashboard now has a select for it, but the mismatch is described in
[09-known-issues.md](09-known-issues.md#4-the-invoice-form-writes-a-name-into-a-code-field).

## The `CUST00000x` scheme

Customer keys are sequential and human-readable, allocated by the dashboard when a new
customer is created. Sequential keys are predictable, which is fine for a course project and
not fine for anything else — they invite enumeration, and if the same scheme were ever used on
a customer-facing identifier it would leak the customer count. Noted rather than fixed.

## The single most confusing field, in the dashboard

`customers` has **two** id-like fields, and they are not the same thing:

- the Airtable record id (`recXXXXXXXXXXXXXX`) — the row's own address, generated by Airtable
- `CustomerId` (`CUST000003`) — a business key, generated by us, and the one invoices reference

The dashboard lists `CustomerId` as its own first column, and the customer form edits it
separately from the record id. Conflating the two was an early bug: the form was writing the
display name into `CustomerId` and invoices stopped matching. The two are now kept apart, which
is what `schema.json` records by listing `CustomerId` as its own field rather than as
`customers.id`.

## VAT

`Price` and invoice totals are stored gross, including 18% Israeli VAT. The net figure is not
stored and is derived where needed by the PDF templates in WF-8, because that is where the
document has to print it. See [07-document-pdf.md](07-document-pdf.md).
